# 登录方案 v2：复刻对标项目的「设备自注册 + 扫码登录」

> 前提变更：**登录按对标项目（hongguo-player）的方法做**，不再用「导入别人账号包」当主路径，也不再做内嵌浏览器点登录。
> 依据：[对标逆向-架构与登录.md](./对标逆向-架构与登录.md)、[重做方案-v2.md](./重做方案-v2.md)
> 本文是**实现方案**，含待探明项与验证实验；不含已落地代码。
> 一句话：**自己注册一台设备，用网页 passport 扫码拿会话；登录态存 Cookie+UID+Token 三件套，业务接口用同一台设备签名。**

---

## 一、目标与不做什么

**目标**

1. 用户点「登录」→ 出现二维码 → 手机 App 扫码确认 → 已登录。全程**不弹浏览器、不输手机号、不换绑**。
2. 登录后可用：收藏、观看历史、预约、追更、点赞、云进度。
3. 换机器后重新注册新设备即可，不复制任何第三方文件。

**不做**

- ❌ 不做网页登录窗口（现有 `main.cjs` 的 `openLoginWindow` 删除）
- ❌ 不做手机号验证码登录（对标项目也要过人机验证：`发送验证码需要人机验证`；留着只会制造 1001/1003 的坑）
- ❌ 不搬 `stealth` / `bosskey` / 规避检测类实现
- ❌ 不复用对标项目的 `hgplayer.db`、`device.json`（这是 v1 方案，已废弃）

## 二、总体流程（四段）

```
① 设备自举  device.json 不存在/过期 → POST /service/2/device_register/
             （请求体 TTEncrypt 加密 + 设备指纹；响应加密回传）
             → 得到 device_id / install_id / cdid / openudid / odin_tt / device_token / ttreq
             → 落盘 device.json（0600）

② 取二维码  GET /passport/web/get_qrcode/
             （先拿 passport_csrf_token，带 x-tt-passport-csrf-token 头）
             → 得到 qrcode 图片（base64 或 url）+ token

③ 轮询      GET /passport/web/check_qrconnect/?token=…
             → 状态机：scanned → confirmed / expired
             → 确认后 Set-Cookie 下发 sessionid / sid_guard / uid_tt / d_ticket /
               passport_csrf_token(_default) / store-region 等

④ 落会话    cookie 逐条合并（不是整串覆盖）+ uid + token + 设备标识
             → 校验 GET /reading/user/info/v1/ → code 0 即登录成功
```

与对标符号一一对应：`deviceBootstrap.ensure` → `QRLoginStart` → `QRLoginPoll`（`QRLoginCancel` 取消）→ `Session.SetCookieString/SetUID/SetToken`。

## 三、数据结构

### 3.1 `device.json`（格式与对标一致，与现有 `session-device.json` 兼容）

```jsonc
{
  "device_id": "…", "install_id": "…", "cdid": "…", "openudid": "…",
  "device_brand": "…", "device_type": "…", "os_version": "…", "os_api": "…",
  "resolution": "…", "dpi": "…", "user_agent": "com.phoenix.read/…",
  "channel": "…", "odin_tt": "…", "device_token": "…", "ttreq": "1$…",
  "store_region": "cn-ha",
  "registeredAt": 0,      // 新增：注册时间（判断是否过期重注册）
  "source": "registered"  // registered | imported（迁移期标记）
}
```

### 3.2 `session.json`（升级为三件套）

```jsonc
{
  "cookie": "sessionid=…; sid_guard=…; uid_tt=…; d_ticket=…; …",
  "uid": "…",
  "token": "…",              // 对标 Session.Token
  "savedAt": 0,
  "source": "qrcode"
}
```

**要点**：`mergeCookies` 而不是覆盖。现有 [store/session.ts](apps/server/src/store/session.ts) 的 `saveSession` 是整串替换，会丢 `store-region`、`passport_csrf_token` 这类持久项。

## 四、模块划分（Electron 栈下）

```
apps/core/src/
├ device/
│   ├ bootstrap.ts     ensure()：有 device.json 且未过期 → ready；否则 register()
│   ├ register.ts      POST /service/2/device_register/（TTEncrypt + 指纹）
│   ├ fingerprint.ts   机型/系统/分辨率/DPI/UA/渠道 的组合（可自定义机型，对标 custom_device）
│   └ pool.ts          install_id 池、备用设备（对标 iidpool/spare）
├ sign/
│   ├ index.ts         签名入口：X-Gorgon / X-Helios / X-Medusa / X-Argus / X-Ladon
│   └ ttencrypt.ts     /service/2/device_register/ 的请求加密
├ login/
│   ├ qr.ts            start() / poll() / cancel()   ← 只做协议，不碰 UI
│   ├ session.ts       cookie 合并、uid/token 落盘、过期判定
│   └ errors.ts        100107 / 7 / 1001 / mfa 的语义化映射
└ crypto/              纯实现，可单测（对标 pkg/crypto）
```

边界：**`login/` 不依赖 UI，`ui/` 只调 `login.start()` 拿二维码数据**。这样 M0 就能先把二维码页做出来（先用假的二维码数据），协议层独立推进。

## 五、待探明项（不猜，靠实验）

> 这三件事决定工作量，必须在动手前用探针跑通；每项都有失败退路。

### L-1 passport 扫码是否需要签名？（半天）

- 实验：用 Node 直接 `GET https://hongguoduanju.com/passport/web/get_qrcode/?aid=8662&…`，带 `x-tt-passport-csrf-token`，UA 用网页版。
- 期望：网页 passport 接口通常是「cookie + csrf」即可，**不校验 App 签名**。
- 若成立 → 登录链路与签名解耦，M5 可提前；若不成立 → 用现有 `hgsigner` 补签（它已验证能过非法应用校验）。

### L-2 TTEncrypt 设备注册能否复现？（2–3 天，最难）

- 目标：`POST /service/2/device_register/` 拿到非 0 的 `device_id`（v1 文档记录：换任意格式返回 `device_id: 0`）。
- 已知：`register: TTEncrypt 加密失败`、`register: 响应解密失败`、`register: 未设置设备指纹`、`register: 序列化 ss_app_log 容器失败`、`header: x-ss-req-ticket`。
- 需要的三样：① `ss_app_log` 容器序列化；② TTEncrypt（AES + 魔改）加密；③ 响应解密（chacha20poly1305 特征）。
- 参考实现：`openhongguo`（Go）里已有 `internal/protocol/sign`，其 TTEncrypt/容器代码是同一族，可移植为 TS 或编译成 wasm。
- **退路**：注册未通前，允许「沿用一份已有设备身份」作为过渡（只读、不写入对方目录），保证 UI 与扫码链路可先联调；注册通了再切换。**这条退路必须写死在代码里可开关，不能变成永久方案。**

### L-3 扫码确认后的 Cookie 集合与 uid/token（1 天）

- 实验：扫码成功后对 `%APPDATA%\hgplayer\hgplayer.db` 的 `account` 行做**只读**对照（不复制），逐条列出 Cookie 名与 `uid`、`token` 来源。
- 目的：确认我们落盘的字段够不够业务接口用（对标 `Session.CookieString/UID/Token` 三件套）。

## 六、失败分支（用户可见的文案）

| 现象 | 判定 | 文案 |
|---|---|---|
| 二维码过期 | `check_qrconnect` 返回过期 | 「二维码过期，点这里刷新」 |
| 已扫未确认 | 轮询状态 scanned | 「已扫码，请在手机上确认」 |
| 未扫就取消 | 本地 cancel | 静默关闭 |
| 需要 MFA | `passport_mfa_retry_tag` 出现 / `flow: 登录失败且非 MFA` | 「账号开了二次验证，需在手机 App 上确认」 |
| 上游限流 | code 7 | 「操作太频繁，等 5~10 分钟」 |
| 设备未就绪 | `device.json` 缺失且注册失败 | 「设备初始化失败，点重试」（对标有 `RetryDeviceRegister`） |
| 会话过期 | 业务接口 100107 | 「登录已过期，重新扫码」 |

**红线**：任何一条失败都不允许把 Cookie / device_token / odin_tt 写进日志（现有日志已注意，重做时保持）。

## 八、验收标准

- [ ] 全新机器：清空数据目录 → 启动 → 点登录 → 二维码出现 → 手机扫码 → 显示昵称/头像 → 收藏列表能拉到数据
- [ ] 重启应用后仍登录（三件套持久化）
- [ ] 断网 → 扫码 → 有明确失败文案，不白屏
- [ ] 二维码过期 → 一键刷新
- [ ] 手动改坏 `device.json` → 自动重新注册，或给出「重试」按钮
- [ ] 日志中 `grep -E "sessionid|odin_tt|device_token"` 零命中
- [ ] 账号写操作（预约/点赞）二次确认（重做底线不变）

| 阶段 | 内容 | 依赖 |
