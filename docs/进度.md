### 六、播放内核（M3 第二步）

**后端**

| 接口 | 作用 |
|---|---|
| `GET /api/play/:episodeId` | 起转码任务（或命中缓存），立刻返回 job |
| `GET /api/prepare/:jobId` | 轮询进度：`queued/working/ready/failed` + 0~1 进度 |
| `GET /api/media/:name` | 视频文件，**只有客户端发了 Range 才回 206**，绝不伪造 |

- `sources/playback.ts`：SDK 取流，优先 720p（≤720 里最高档），拿 `decryptionKey`
- `media/transcode.ts`：下载加密原件（0~45%）→ `ffmpeg -decryption_key <hex> -c:v libx264 -crf 23`（45%~99%）→ 缓存复用；按字节上限 prune
- `media/jobs.ts`：一集一 job、同集单飞、job 表上限 60

**前端**：`views/Play.tsx` + `design/play.css`

- 路由 `#/play/:seriesId/:episodeId/:no`，全屏渲染（不显示顶栏/胶囊导航）
- 首次进入显示「正在准备这一集」+ 进度条，转好自动播
- 控制条：上一集 / 播放暂停 / 下一集 / 时间 / 进度 / 音量 / 倍速（1→1.25→1.5→2）/ 全屏；鼠标静止 2.5s 自动隐藏
- 键盘：空格播放、←→ 5 秒、F 全屏、Esc 返回
- 全屏优先走窗口级（`window.yimu.setFullscreen`），浏览器里退回 `requestFullscreen`

**实测**：第 1 集 → 720p / 1280×720 / 154 秒 / 22.7 MB；`readyState=4`，能播能暂停；
`Range: bytes=0-1023` → `206` + `content-range: bytes 0-1023/22717331`。

> 环境坑：这台机器的沙箱里 **ffmpeg 子进程写不了 `%APPDATA%`**（node 可以），
> 所以本地验证时核心要用 `HORUN_DATA_DIR=D:\红果短剧\data` 跑；桌面壳本来也落在这里。

### 十二、三个反馈修复（v0.28.1）

| 反馈 | 根因 | 修法 |
|---|---|---|
| 全屏后再点全屏取消不了 | 播放页只查了一次 `isFullscreen()`，**没订阅 `yimu:window-state`**，`fullscreen` 状态永远是 false，第二次点击仍传 `true` | 订阅 `onWindowState` 同步状态；按钮标题随状态变成「退出全屏」 |
| 返回主页面仍是全屏 | 离开播放页时没有退出窗口全屏 | 新增 `exitFullscreen()`：返回按钮 / Esc / 组件卸载三处都调；卸载时只在**真的离开 `#/play/`** 才退（切下一集不打断全屏） |
| 小窗模式在播放窗口用不了 | 播放页控制条没有小窗入口（只有顶栏有，而播放页不显示顶栏） | 控制条加「小窗播放」按钮 → `yimu:openMini({seriesId,episodeId,no})`；小窗页面（`?mini=1`）在 `loadedmetadata` 时回报真实宽高，窗口贴合比例 |
| 主进程弹「A JavaScript error occurred」`EPIPE: broken pipe` | GUI 启动（双击 exe）没有控制台，主进程把核心子进程日志 pipe 到 `process.stderr` → 写失败抛异常 | 启动时吞掉 stdout/stderr 的 `error` 事件 + 全部 `console.*` 包一层 try/catch + `safeLog()` |

全屏状态下点返回 → `hash=#/` 且窗口宽回到 1362；小窗按钮存在，点击后页面数 1 → 2。

**产物**：`apps/desktop/release/HorunDrama Setup 0.28.1.exe`（145.0 MB）

| 控制 | 悬停才出现：上一集 / 播放暂停 / 下一集 / 标题集数 / 还原 / 关闭 |
| 交互 | 整窗可拖；双击画面还原；底部 2px 进度线 |
| 行为 | 打开时主窗口自动暂停；关闭小窗自动恢复；带入当前播放位置（`?t=`） |

**拖动为什么之前不能用**：原来靠 CSS `-webkit-app-region: drag`。它只在一块矩形内生效
（播放页没顶栏 → 无处可拖；小窗只有 22px 的条），而且会吞掉鼠标事件，跟"点画面暂停 /
双击还原"冲突。改成**手动拖动**：渲染进程按下 → IPC → 主进程按光标 `setInterval` 跟随
`setPosition`，松手/失焦即停。顶栏、播放页、小窗三处都走同一套 `useWindowDrag()`。

**"拖动时莫名其妙放大"的根因**：小窗当时是 `resizable: true`，无边框窗口边缘自带
resize 热区；用户从边上按下时系统先按"拉伸"处理，再叠加我们的拖动循环，看起来就是越拖越大。
改法：小窗 **固定尺寸（`resizable: false`）**，尺寸只由视频比例决定。

**实测**：主窗口拖动位移 `27,208`；小窗拖动位移 `-140,-60`（与光标位移一致，且尺寸不变）；
还原关闭后窗口数 2 → 1；开小窗时主窗口 `paused=true`。

**产物**：`HorunDrama Setup 0.28.3.exe`（145.9 MB）

### 十四、拖动问题定论（v0.28.6）

**现象**：长按或拖动窗口时，窗口莫名变大；主窗口、播放页、小窗都有。

**根因（Electron 已知问题）**

- Electron 41.3+ 起，无边框窗口（`frame: false` + thickFrame）带有**外扩的 resize 边框 / input insets**，
  HWND 实际矩形会比 `getBounds()` 大一圈：electron [#51679](https://github.com/electron/electron/issues/51679)、
  [#51252](https://github.com/electron/electron/pull/51252)、[#50864](https://github.com/electron/electron/pull/50864)
- 我们此前用「定时器轮询光标 + `setPosition`」手动挪窗口，和这圈边框抢几何 → 尺寸被系统拉伸，
  表现就是"长按/拖动时窗口自己变大"

**成熟项目怎么做（VS Code / Discord）**

**不自己挪窗口**。用 `-webkit-app-region: drag` 标出可拖动区域，交给 Windows 走原生 HTCAPTION 拖动；
交互元素标 `no-drag`。窗口位置/尺寸完全由系统维护，天然不会变大。

**最终实现**

| 位置 | 做法 |
|---|---|
| 主窗口顶栏 | `.topbar { -webkit-app-region: drag }`；按钮/搜索/自绘窗口按钮 `no-drag` |
| 播放页 | 顶部 28px 透明拖动条（`app-region: drag`），不影响画面点击 |
| 小窗 | 顶部 28px 拖动条（悬停显示把手），同样是原生拖动 |
| 手动拖动 | **全部删除**（`useWindowDrag` 与 `setPosition` 拖动 IPC 不再使用） |

保留了自绘窗口按钮与玻璃顶栏外观（是用户偏好的那版视觉）。

**验证**：主窗口顶栏计算样式 `-webkit-app-region: drag`；小窗拖动条 28px / `drag` / `pointer-events: auto`；
用户实测：主窗口、播放页、小窗均可拖动，长按不再变大，顶部透明效果保留。

**产物**：`HorunDrama Setup 0.28.6.exe`（149.5 MB）

### 三、踩过的坑

1. **ffmpeg 靠扩展名猜封装格式**：临时文件写成 `.mp4.part` 会报

## 2026-11-16 · 画质增强（转码降噪 + 锐化）

### 选型依据（从 GitHub / FFmpeg 文档学）

- [Anime4K](https://github.com/bloc97/Anime4K)：GLSL 实时超分/降噪，主要面向**原生 1080p 动画**，
  且要在播放器里跑 shader；我们这条链路是 ffmpeg 离线转码真人短剧，直接搬不合适
- FFmpeg CAS（`cas=strength=0.5`）效果好，但**仓库自带的 ffmpeg 是 2018 版，没有 cas 滤镜**（已用 `-filters` 确认）
- [ffmpeg-production 的滤镜链](https://github.com/Galbaz1/video-research-mcp/blob/d4908c4d65ebcbfb8fb65dc95d95a314e91d273a/skills/ffmpeg-production/SKILL.md)：
  `hqdn3d` 降噪 + `scale=flags=lanczos` + `unsharp` 锐化，是这套老 ffmpeg 能用的稳妥组合

### 实现

- 设置新增 `enhanceVideo: off | standard | strong`，设置页「画质与下载」里有下拉
- 转码时按档位加滤镜：
  - standard：`hqdn3d=1.5:1.5:6:6,unsharp=5:5:0.7:5:5:0.0`
  - strong：`hqdn3d=2:2:8:8,unsharp=5:5:1.1:5:5:0.2`
  - 开启时 CRF 从 23 收到 21，减少二次压缩损失
- 缓存路径带后缀（`<id>-720p-standard.mp4`），切换档位不会错误复用普通转码；播放/下载都走同一套

### 实测

- 触发转码后 core 日志：`画质增强=standard 滤镜=hqdn3d=1.5:1.5:6:6,unsharp=5:5:0.7:5:5:0.0`
- 文件：普通 720p **22.1 MB** → 增强版 **31.6 MB**；播放 URL 变成 `-720p-standard.mp4`
- 同一帧（20s）清晰度指标（Laplacian 方差）：**595.87 → 1461.67（约 2.45×）**，亮度标准差 61.1 → 62.0
- 对比图：`docs/screenshots/m4-enhance-compare.png`（左普通、右标准），设置页：`m4-settings-enhance.png`
- 测试完设置已恢复 `off`

## 2026-11-16 · 播放卡顿 + 「上游没有可播放的清晰度」修复（秒开 + 自动升清）

### 现象

1. 每点一集都要等几十秒（下载加密原件 + 整集 ffmpeg 转码，播的其实是本地文件），用户反馈「播放器太卡」。
2. 从 18:30 左右开始，任何一集都报 **`上游没有可播放的清晰度`**，完全不能播。

### 定位

- App 源 `POST /novel/player/video_model/v1/`（SDK `resolvePlayback`）现在**稳定返回 HTTP 200 + 空 body**，
  body 为 `{"biz_param":{"video_id_type":0,"need_all_video_definition":true,"video_platform":3},"video_id":"<集 id>"}`。
  `content-length: 0`、`tt_stable: 1`，x-argus / x-ladon 都是真签名（不是旧的四字节 stub）。
  同机 `data/cache/media` 里 10:38~12:01 转出来的 720p/1080p 说明**当天早些时候这条链路是通的**，
  所以是上游在下午改了策略（匿名设备取流被静默拒绝），不是签名写错。
- 交叉验证过、都还是空 body 的组合：
  - 换 host：`api5-normal-sinfonlinea` / `api5-normal-lq`
  - 换版本：`7.3.9.32` / `7.4.3.32`（version_code / manifest / update_version_code / pv_player 一起改）
  - 带 `/ 不带` 游客 cookie（install_id / ttreq / store-region）
  - `/novel/player/multi_video_model/player/v1` + `mixed_video_id_map`（对标客户端用的那个）
  - 带 / 不带 `x-medusa`
  → 结论：**匿名这个身份现在拿不到播放模型**，签名与接口形状不是根因。
- 慢的根因和上面无关，是设计问题：App 源是 HEVC + CENC，浏览器放不了，
  只能「整集下载 → libx264 转码 → 播本地 mp4」，所以必然要等。

### 方案（快路径优先，慢路径兜底）

新增 `apps/core/src/sources/webplay.ts`：官网 H5 播放器的兜底接口

```
POST https://hongguoduanju.com/api/video/protected/fallback-play-info?aid=8662
body: {"item_id":"<集 id>"}
→ { main_url, url_expire, base_resp }
headers: content-type: application/json, x-xs-from-web: 1, UA 用桌面 Chrome
```

- 返回的是**明文 H.264 High + AAC 的 mp4**（360×640，约 550~700kbps），不加密；
- CDN 支持 `Range`（206）、`accept-ranges: bytes`，`access-control-allow-origin: *`，可拖进度；
- 单集约 180~250ms，同一集短时间内返回同一地址，`url_expire` 约 1 小时；
- 只给一档 360p；高清仍然只能走 App 源转码。

播放计划（`media/jobs.ts` 的 `startEpisode`）改成三级：

1. **本地缓存优先**：`existingMediaAny()` 命中任意清晰度就直接播本地，**不发任何上游请求**（34ms）；
2. **秒开**：官网 360p 直连（`mode: direct`），起播约 1~2s；
3. **后台升级**：`upgrade=1` 时同时起 App 源转码任务，转好后前端无缝换源（保留播放位置）；
   上游还是空响应就静默保持 360p（选了高清会提示"暂时取不到，先用流畅播放"）。

配套改动：

- `GET /api/stream/<集 id>`：**同源代理**。不能把 CDN 地址直接给 `<video>`——
  CDN 对浏览器发的 `Referer: http://127.0.0.1:5880/…` 返回 **403**，Node 侧不带 Referer 才 200。
  代理保留 Range/206 语义，遇到 403（地址过期）自动重取一次再重放。
- `router.match` 支持 HEAD → 复用 GET 处理器（`/api/stream` 的 HEAD 探测要能过）。
- 转码编码器自动挑：`ffmpeg -encoders` 里按 **NVENC → QSV → AMF → libx264** 选第一个可用的，
  跑失败了自动退回 libx264（本机 RTX 4060 走 `h264_nvenc`）。
  `-preset p4 -tune hq -rc vbr -cq 23 -b:v 0`。
- 下载（`media/downloads.ts`）：App 源取不到就退到官网直连下载（不转码），
  文件名带 `-360p`，实测 12.5MB 的集 2 秒写完。
- `QualityPref` 增加 `smooth`；自动 = 「缓存优先 + 360p 秒开 + 后台升 720p」。
- 前端控制条实时显示**当前真正在播的画质**（`.xg-extras__def`，自动升清后会变）。

### 实测（dev core 5881）

| 场景 | 结果 |
|---|---|
| 未缓存集 `quality=auto` | `mode=direct`，首次 1040ms（含取地址），之后 10ms；起播约 1~2s |
| 已缓存集 `quality=auto` | `mode=file`，34ms，直接是本地 1080p |
| `/api/stream` HEAD / Range | 200 `video/mp4` `content-length=12505314` / 206 `bytes 1000-1999/12505314` |
| 浏览器实播 | `readyState=4`、`duration=143.77`、360×640、seek 到 60s 继续播、无错误 |
| 推荐页 | 命中缓存 720p，秒开 |
| 下载 | 360p 直连，2 秒完成，落盘 12.5MB 可播 |
| 高清升级 | 当前上游空响应 → 后台任务静默失败，保持 360p |

### 还没解决（交给下一轮）

- **720p/1080p 现在拿不到**，因为 App 源匿名取流被拒。可能的方向：
  - 用**账号会话**去取流（现在的 `video_model` 走的是匿名 SDK 设备，没带账号 cookie）；

## 2026-11-16 · 高清通道打通 + 播放页/布局/停靠栏的一轮整改

### 一、高清通道（720p/1080p）真的找到了

参考 `D:\AAAtest\11111` 引导去看了开源实现（本地副本 `.research/hongguo-web`，MIT）：
它把红果 App 的播放链路完整打通了，关键结论全写在那份代码的注释里：

1. 2026-10-27 起，上游会**校验播放请求的设备身份**：随机合成的 iid/device_id 会被
   软拦截成 `HTTP 200 + 0 字节`。必须调 `device_register` 注册匿名设备。
2. 2026-11-02 起还要**六个签名头**（x-gorgon / x-khronos / x-ladon / x-argus / x-helios / x-medusa）。
3. 2026-11-10 起正文要 **gzip**（`Content-Encoding: gzip`，x-ss-stub 对压缩后的字节算），
   播放客户端版本 `74332 / 7.4.3.32`（UA、query、签名内三处一致），
   并且**每次取流要注册全新身份**（同一身份短时间重复取流会被判重 → 空响应）。
4. 空响应还有一条兜底：签名 **GET** `/reading/bookapi/video_tab/multi_video_model/v1/`
   （73932 版本字段、无正文、带 `x-tt-request-request-tag`），响应在
   `data.video_model_data[vid].video_model`。
5. `video_model.encrypt_info.spade_a`（base64）→ 纯字节变换解包出 **content key**
   （32 位 hex），配合 MP4 的 `senc` 逐样本 IV 做 AES-128-CTR 解密。

这正是我们一直「上游没有可播放的清晰度」的根因：**openhongguo SDK 走的是
常驻匿名设备 + 未压缩正文的老 POST**，被上游稳定软拦截。

实现（新增 `apps/core/src/sources/appplay.ts` + 内嵌 `apps/core/src/upstream/hongguoweb/`）：

- 复用 hongguo-web 的 MIT 代码（签名 / 设备注册 / spade 解包 / App 取流），
  清单与 GPL 注意点见同目录 `NOTICE.md`；
- 我们这层做了：结果缓存 20 分钟、全局串行 + 1.5s 间隔（防判重）、
  连续 2 次空响应就熔断 3 分钟（不把上游打爆，也不让用户干等）；
- `sources/playback.ts` 先走这条新链路，SDK 那条路降级成兜底；
- ffmpeg 用 `-decryption_key <hex>` 解密：**源是 H.264 时只 `-c copy` 重封装**
  （实测 143s/720p：1.4s）；HEVC(bytevc1) 才转码（实测 libx264 veryfast：6.9s）。

实测（2026-11-16 19:17~19:19，同一网络）：

```
auto    584ms  codec=bytevc1 def=1080p 17.9MB  key=ok
480p   1416ms  codec=bytevc1 def=480p   6.9MB  key=ok
720p   1426ms  codec=bytevc1 def=720p   9.0MB  key=ok
下载加密原件 1.0s + libx264 转码 6.7s → 24.9MB、720×1280 H.264，可播
```

### 二、高清：不是我们代码的问题，是上游在拦这台机器

用户反馈「别人不登录就能选 720p/1080p」，所以直接做了三组对照：

1. **直接问对标客户端**（`短剧播放器.exe` 的 Wails 绑定 `PlayInfo`）：
   它返回了 5 档（360/480/540/720/1080，bytevc1）—— 但注意它的 url 全是
   `http://127.0.0.1:<port>/media/<vid>/<quality>`（它自己的本地代理），
   说明这是**本地缓存/已取过的模型**，不是刚打上游拿到的。
2. **抓它的真实请求**（`GODEBUG=http2debug=2` 重定向到 `.tmp/hg-live.err`）：
   它打的是 `POST /novel/player/multi_video_model/player/v1`（注意是 `/player/v1`，
   不是我们 SDK 的 `/v1/`），**未压缩 JSON 正文**、`content-length: 279`、

   解码验证过：`wun6ag==`→1794828738）。
   关键：**它的响应是 `HEADERS flags=END_STREAM`，即 200 + 0 字节** —— 它也没拿到。
3. **用它的身份完全照抄一发**（它的 device_id/iid/cdid/device_token/UA/cookie +
   同样的 path/query/body/占位签名）：`status 200 len 0`。用我们自己的新设备也是 0。

结论：上游现在对**这台机器的出口 IP** 的匿名播放请求一律 200 + 空 body，
和对标客户端一视同仁；它界面上还能选 720p/1080p 是缓存。我们 19:17 实测能拿到
720p/1080p（含密钥）也是真的，是 19:19 之后开始被拦的（短时间内取了十几次）。

- `appplay.ts` 熔断改指数退避：2 → 4 → 8 → 16 → 30 分钟（上限 30），
  成功一次立刻回到 2 分钟。避免隔 3 分钟就去撞一次、把配额耗光。

1. **登录后仍不行**：用我们自己的账号会话（`session.json` 的 cookie + `session-device.json`

## 2026-11-16 · 双击全屏修复 / 撤掉「借本机」/ 取流机制调研与优化

### 一、双击全屏"进一下就退"（真 bug）

### 三、GitHub 调研结论（为什么不能"照抄成熟项目"）

| 项目 | 状态 |

## 2026-11-16 · 高清取流真正修好（反编译对标客户端签名）

### 根因（用签名对齐测试定位）

把对标客户端抓到的一次真实播放请求原样喂进我们的签名实现，逐头比对：

| 头 | 结果 |
|---|---|
| `x-ladon` / `x-argus` | **完全一致**（4 字节 ts 占位） |
| `x-helios` | 不一致（48 字符 base64） |
| `x-medusa` | 不一致（1048 vs 1032 字符） |
| `x-gorgon` | 不一致（52 hex） |

进一步查发现两层问题：

1. **我们的播放请求根本没发 `x-gorgon` / `x-helios` / `x-medusa`**：
   移植来的 `app-source.js` 只合并了 `PlaybackSign.signPlayer`（只产出
   argus/ladon/khronos/req-ticket）。对标的请求一定带这三个头 → 上游判签名无效，
   回 `200 + 0 字节`。
2. **`helios` 的 license 常量是错的**：原实现用 `1588093228`。反编译
   `crypto.heliosWith` 看到明文是 `fmt.Sprintf("%d-%d-%d", ts, license, aid)`，
   再用「块密码可逆」把客户端真实 x-helios 解出来，明文是
   `1794828738-646637794-8662` → license = **646637794**。

### 做法

- `pure-sign.js`：license 改成 646637794；
- `app-source.js`：请求头补上 `x-gorgon` / `x-helios` / `x-medusa`（来自 `PureSign.sign`）；
- 验证工具留在 `.tmp`：
  - `go-pclntab2.py`：解析 Go pclntab，导出 2 万多个函数名与地址；
  - `go-disasm.py`：capstone 反汇编并解析 CALL / RIP 常量；
  - `sign-align.mjs` / `helios-decrypt.mjs`：用客户端真实请求做签名对齐与参数反解。

### 验证

| 场景 | 结果 |
|---|---|
| 修好后 `/api/upgrade/...&quality=720p` | 1231ms 返回任务，**1080p + key ok**，转码 8s，落盘可播 |
| 同一时刻旧写法（不带三个头） | `200 + 0 字节`（对照实验，证明就是签名问题） |
| 播放页 | 360p 秒开 → 后台升清 → 无缝换 1080p |

也就是说：**高清不再受"上游限流"影响，是我们自己的签名写错了。**
之前偶尔能成功（20:21 那次）是撞上了服务端的宽松窗口。

### 补充：打包版还差一个 SM3

修完签名后 dev 核心能取到 1080p，但**打包版仍然失败**。排查发现：
Electron 自带的 Node 用 BoringSSL，`crypto.createHash('sm3')` 直接抛
`Digest method not supported`；而 `pure-sign.js` 和 `playback-sign.js` 都依赖 SM3
（x-medusa 链路），所以打包版 appplay 一直失败，而用系统 Node 跑的 dev 核心正常。

处理：新增 `core/sm3.js` —— 有原生 sm3 就用原生，没有就降级到纯 JS 实现
（已与 `node:crypto` 在空串 / 中文 / 长文上逐字节对齐），两个签名模块都改为引用它。
在 Electron 运行时下实测 `AppSource.fetch` 成功，打包版 `/api/upgrade` 1015ms
拿到 1080p。

## 2026-11-16 · 高清「秒进」优化：HEVC 直接搬运 + 下一集预转码

### 为什么之前慢

对标客户端「点开就是高清」，是因为它**不转码**：直接用设备解码器播 HEVC + CENC 流，
拿到内容密钥就能边下边播。我们是把整集下载下来、用 x264 重编码成 H.264 再播，
1080p 一集要 8~18 秒。

### 这轮做了两件事

1. **能硬解 HEVC 时只解密 + 重封装（`-c copy`）**，不再重编码：
   - 前端探测 `CAN_PLAY_HEVC`（Chromium 的 `canPlayType`），请求带 `hevc=1`；
   - 转码层认出 HEVC 源就 `-c copy`，产物存 `<集>-<档位>-hevc.mp4`，
     与 H.264 版本分开存 —— 不能硬解的客户端仍会走重编码，不会播到解不了的文件；
   - 实测：同一集 1080p 从 ~10s 降到 **1.8~2.4s**（网络快时），画质零损失。
2. **下一集后台预转码**：播到 25 秒时对下一集直接起高清任务（同时预热 360p 地址），
   切下一集时通常是「已缓存」，不用等。

### 实测（打包版）

| 场景 | 时间 |
|---|---|
| 已缓存集起播 | 500ms 内出画面（readyState=4） |
| 未缓存 1080p（网络快） | 1.8~2.4s 完成「下载 + 搬运」 |
| 未缓存 1080p（网络一般） | 8~11s，瓶颈是下载整个文件 |

### 还能再快的一步（未做）

真正能做到 ~1s 的是 **MSE + ClearKey 直接播加密源**：本机 Electron 已确认支持
HEVC 硬解与 `org.w3.clearkey`（都实测过），CENC 结构也友好
（`schm=cenc`、`tenc` 里 KID 可解析、moov 在文件头）。
也就是不下载整集、不解密落盘，直接把上游流喂给 MSE 用内容密钥解锁 ——
而且进度条可拖（原始 mp4 带完整索引）。

## 2026-11-16 · 高清「秒开」：边解密边封装的直播流（首帧 ~2.6s）

### 先说结论：为什么没用 MSE + ClearKey

本来打算用 MSE + ClearKey 直接播加密源，但实测有两个硬限制：

1. 上游给的是**非分片 mp4**（`moov` + 一个大 `mdat` + `senc`），Chrome 的 MSE 只接受
   **fMP4**（`moof` 分片）；非分片 mp4 只能走 `src=` 播放，而 Chromium 的 EME 又要求走 MSE；
2. 要想把这份文件变成 fMP4 又保留 CENC 加密样本，ffmpeg 做不到
   （`-c copy` 不能复制"加密样本 + senc"），需要自己写分片器，成本远超收益。

所以改成**「边解密边重封装成 fMP4」直推给浏览器**：效果一样（点开就播、硬件解 HEVC、
不落盘等待），实现还更简单。

### 实现

- `core/src/media/live.ts`：`ffmpeg -decryption_key K -i <上游 url> -c copy
  -movflags frag_keyframe+empty_moov+default_base_moof -f mp4 pipe:1` → 直接写 HTTP 响应，
  客户端断开就杀进程；
- `GET /api/live/:episodeId?quality=`：先取流（appplay 缓存），再开始推流；
- `/api/play?live=1&hevc=1`：**立即**返回一个 `direct` job 指向 `/api/live/...`（20ms），
  同时后台异步起完整缓存任务；缓存好了前端换源（保留播放位置），拖动/续播不受影响；
- 播放页专用（`live=1`），推荐页仍走 360p + 后台缓存 —— 滑动场景不适合起解码管线；
- 秒开流失效时前端自动退回普通线路（`liveFallback`），不会卡在错误提示上。

### 实测（打包版，未缓存的新集）

| 指标 | 结果 |
|---|---|
| `/api/play` 响应 | **20ms**（返回 live 地址） |
| `/api/live` 首字节 | **190~500ms**（热）/ ~1.5s（冷） |
| 1080p 首帧 | **2.2~2.6s**（含页面与剧集详情加载） |
| 换成完整缓存 | ~13s，位置不丢，之后可任意拖动 |
| 对比：改造前 | 8~18s 才能出画面 |

### 顺带修的

- appplay 增加 single-flight：同一集同一档位并发请求合并，秒开流和后台缓存不会各发一次；
- 默认清晰度 1080p，上游缺档自动降级；
- HEVC 源只解密+搬运（`-c copy`），不重编码 —— 画质零损失。

## 2026-11-16 · 预加载前后各 N 集 + 推荐页全屏进度条归位

### 一、预加载（默认前后各 5 集，可在设置里改）

## 2026-11-16 · 小窗和播放页取流统一 + 全屏保留操作栏/弹幕 + 闲置自动隐藏

### 一、为什么"小窗"（推荐页）慢、播放页快

上一版为了降低滑动时的开销，把"边解密边播"的秒开流只开给了播放页（`live=1`），
推荐页还是走「官网 360p 直连 + 后台转码」。官网 360p 偶尔取不到时，推荐页就会
退化成"下载整集 + 重封装"才开始播 —— 这就是你看到的小窗要等很久。

现在两处统一：推荐页也带 `live=1`，点开就是 1080p 秒开流，后台照样落一份完整缓存。
实测未缓存集：**推荐页首帧 1.87s**（`/api/live/...?quality=1080p`），播放页 ~2.2s。

### 二、全屏后操作栏 / 弹幕消失

根因：全屏元素原来是**播放器自己**（`.xgplayer`），而点赞/评论/收藏/分享/下载栏、
弹幕层、简介都在播放器子树**外面**，浏览器渲染全屏元素时只画它自己的子树 —— 所以全没了。

修法两层：

1. `DramaPlayer` 新增 `fullscreenHost`，双击全屏时对**页面容器**（`.play` / `.feedv`）调用

2. xgplayer 自带的全屏按钮用它的 `fullscreenTarget` 配置指向同一个容器

### 三、切下一集后"弹回窗口"

同一个根因的另一种表现：全屏元素若是播放器，切集时播放器被销毁重建 →
浏览器自动退出全屏。宿主改成页面容器后，容器在整个播放页生命周期里都不重建，
实测切集后 `document.fullscreenElement` 仍是 `.play`，视频继续播。

### 四、闲置自动隐藏（弹幕保留）

- 播放页原有 `chromeVisible`（2.6s）扩展到**控制条**：闲置时控制条一起淡出，
  鼠标一动立刻回来；
- 推荐页新增同一套 `wake()`：闲置 2.6s 隐藏右侧操作栏 + 底部信息 + 控制条；
- 弹幕层不参与隐藏（用户明确要求全屏时弹幕保持可见）。

实测（打包版，聚焦仿真）：闲置 3.2s 后 `.play__rail` / `.xgplayer-controls` 的

## 2026-11-16 · 去掉重复的"小窗"按钮 + 画中画切集不再被打断

### 一、两个按钮功能重复

顶部栏那个"小窗"是我们自己做的桌面小窗（`window.yimu.openMini`，依赖桌面宿主），
底部控制条那个是 xgplayer 自带的**画中画**（标准 PiP）。按用户要求删掉顶部的，
保留画中画。

### 二、切集后画中画自动取消（bug）

根因：切集时播放页把 `job` 清空 → `readyUrl` 变空 → `DramaPlayer` 被卸载 →
媒体元素销毁 → 浏览器顺手关掉画中画（全屏也会一起退）。

修法两处：

1. `Play.tsx` 切集时**不再清空 job / startReady**，并保留"上一集可播地址"
   （`lastPlayableUrl`），新集还在准备时继续用旧源播，就绪后再换；
2. `XgPlayer.tsx` 不再因为 `url` 变化销毁播放器，改成 `player.src = url`
   **原地换源**（媒体元素保持同一个）。换源后的第一次 `canplay` 才恢复起播位置/倍速，
   避免每次 `canplay` 都把用户拖回去。

### 三、画中画里也能切集

注册了 `navigator.mediaSession`：

- `metadata` 显示「剧名 + 第 N 集」+ 封面；
- `nexttrack` / `previoustrack` 映射到上一集/下一集，`play`/`pause` 映射到播放控制。

这样画中画窗口所在系统媒体控件（Windows 音量浮层、蓝牙耳机按键）也能切集。

### 实测（打包版）

| 步骤 | 结果 |
|---|---|
| 点控制条画中画按钮 | `document.pictureInPictureElement` = video，播放 1080p |
| 画中画中切下一集 | **仍是同一媒体元素**、PiP 保持、新集继续播（3.5s → 7.5s） |
| 顶部"小窗"按钮 | 已移除（`[title="小窗"]` 数量 0） |
| mediaSession 元数据 | 「全球死考：刚下刑场你让我去考试一季 第 312 集」 |

## 2026-11-16 · 修「播完不自动切集、只显示重播」

### 现象

一集播完停在 `重播` 按钮上，不自动下一集；有时候路由已经切到下一集了，
画面却还是上一集的重播画面。

### 两个根因

1. **换集用的是 `player.src = url`**。xgplayer 在 `ended` 状态下会忽略这次赋值
   （它认为要等用户点重播），于是路由变了、播放器还停在旧的媒体上，弹着重播按钮。
   成熟做法（video.js / hls.js / xgplayer 播放列表示例）都是**保留同一个媒体元素、
   换 `video.src` 后 `load()` 再 `play()`**，不依赖播放器自己的状态机。
2. **缓存里存在被掐断的文件**。上游偶尔提前关门，下载只拿到一部分，ffmpeg 照旧解出
   前几秒并写成"完成品"（实测有一集缓存只有 8 秒，正片 47 秒）。这种集播几秒就结束，
   看起来就是"一集刚开始就弹重播"。

### 修法

- `ui/XgPlayer.tsx`：换集时 `player.pause()` → `media.src = url` → `media.load()` →
  `media.play()`；元素不重建，画中画/全屏依旧保留。换源后的第一次 `canplay`
  才恢复倍速/起播位置（避免把用户拖的进度条顶回去）。
- `media/transcode.ts`：
  - `download()` 校验 `content-length`，不够就报"下载不完整"，不拿半截文件去转码；
  - 转码完成后比对源与产物的 `mvhd` 时长（自己解析 moov，不依赖 ffprobe），
    产物明显偏短就删掉并抛错，下次重下重转。
- 缓存里已有的坏文件手动清掉（扫了 87 个，删了 1 个 8 秒的）。

### 验证（打包版 v1.1.1）

| 步骤 | 结果 |
|---|---|
| 第 341 集（77s）播到底 | 路由 → 342 |
| 342 的源 | `7697465287901203481-1080p-hevc.mp4`（已切换） |
| 播放 | t=1.7 正常推进，`重播` 按钮 display=none |

`electron-builder` 要从 GitHub 下 `electron-v45.3.2-win32-x64.zip`（151MB），

## 2026-11-17 · 自动下一集彻底修好（不再停在"重播"）

### 上一版为什么没修干净

上一版只换了换源方式（`media.src` + `load()`），解决了"路由切了、画面留在上一集"。
但**"播完完全不切、只弹重播"**还有一层原因：`onEnded` 里有两道静默判空：

```tsx
if (prefs?.autoPlayNext === true && detailRef.current !== null) neighbor(1);
```

- `prefs` 来自 `/api/settings`，加载失败/慢 → 是 `null` → `=== true` 不成立 → 不切；
- `detailRef` 来自 `/api/series`（786 集的大 JSON），接口抖动 → `null` → 不切。

两种情况都**没有任何提示**，用户看到的就是"播完了、弹重播"。
（我用 CDP 把 `/api/settings` 和 `/api/series` 都改成 500，稳定复现了这个现象。）

### 这版怎么改

1. **只有明确关闭才不切**：`prefs?.autoPlayNext === false` 才 return，`null` 按默认开处理；
2. **剧集列表三级兜底**：当前 detail → 内存/localStorage 缓存（`horun-detail:<seriesId>`）→ 现拉一次；
   全失败才提示"拿不到剧集列表，请点选集手动切"；
3. **切集过渡层**：播完立刻盖一层「正在加载下一集…」（同时把 xgplayer 的重播浮层压掉），
   路由真的换到下一集才撤掉；6 秒还没好就明确提示，而不是让重播按钮骗人；
4. **准备失败兜底 360p**：高清/秒开流都起不来时，自动退官网 360p 直连，至少能接着看；
5. 换源后同时调 `player.play()`，确保播放器状态机离开 ended。

## 2026-11-17 · 自动下一集真正的根因：播放器只创建一次，回调却停在"第一次渲染"

### 现象（用户："以前的版本都能自动切集，现在播完停在重播"）

CDP 连 headless Edge（9338），页面停在 `#/play/...`，连续把结尾拖掉（`.tmp/probe-end2.mjs`）：

| 轮次 | 结果 |
|---|---|
| 进入页面后第 1 集播完 | 自动切到下一集 ✅ |
| 第 2 集播完 | **路由不变**，`.xgplayer-replay` 又出现，过渡层闪一下就消失 ❌ |
| 第 3 集及以后 | 同样不切 |

即 **每次进播放页只能自动切一次**。上一个 AI 每轮都重新 `Page.navigate` 再测，
测到的永远是"第一次"，所以怎么测都通过。

### 根因

`ui/XgPlayer.tsx` 的播放器实例只创建一次（`useEffect(..., [])`），
`player.on('ended', () => onEnded?.())` 这类绑定拿到的是**挂载那一刻那次渲染的 props**。
而 `Play.tsx` 的 `onEnded` 调 `neighbor(1)`，`neighbor` 依赖 `route.episodeId`：

- v1.0.0：切集时 `setJob(null); setStartReady(false)` → 播放器被卸载重建 → 每次都是新闭包 → 一直正常；
- **commit `1108be9`（"画中画切集不再取消"）** 为了让画中画/全屏在换集时不被打断，去掉了这两行，
  播放器改成原地换源。于是 `onEnded` 永远停在**进入页面那一集**的 `route`：
  `neighbor(1)` 算出的是"第一集的下一集"，从第二集开始就等于把 hash 设成当前集 →
  路由不变 → 结束状态不解除 → 只剩「重播」。

`onTime`（25 秒预热下一集、跳片尾）也是同一份旧闭包，同样只在第一集生效过。

### 修法

`ui/XgPlayer.tsx`：把 `onReady / onTime / onEnded / onPlaying / onError / rate` 放进 `cbs` ref，
每次渲染刷新，事件里一律读 `cbs.current.xxx`。播放器仍然只创建一次（画中画、全屏都保得住）。

### 顺带修掉的第二个坑：并发转码把缓存文件写坏

修完回调后，第一次切集稳定报
`PipelineStatus::PIPELINE_ERROR_DECODE: Failed to send audio packet ... timestamp=-23220`。
拿 ffmpeg 一看：`Found duplicated MOOV Atom. Skipped it` —— 产物里有**两个 moov**，
是"两个 ffmpeg 同时写同一个 `.part.mp4`"拼出来的。这类文件 mvhd 时长正常、大小校验也过，
浏览器却直接解码失败 → 表现为"切到下一集就播放失败"。

为什么会有两个：`startAppJob()` 先 `await resolveEpisodeStream()`（约 1 秒）、
**之后**才 `INFLIGHT.set(key, ...)`。页面加载时 `/api/play`（秒开任务内部会 `startUpgrade`）
和 `/api/preload`（预加载队列）几乎同时请求同一集同一档 → 两个请求都卡在 await 里、
都通过"没有在跑"的检查 → 各起一个 ffmpeg 写同一个文件。

三处修改：

1. `media/jobs.ts`：`INFLIGHT` 改成 `Map<string, Promise<Job>>`，占位在**同步**阶段就写进去
   （`startAppJobInner()` 返回的 promise 立刻 `INFLIGHT.set`），并发者直接等同一个 promise；
   转码中的占位由 `runTranscode` 结束时清。
2. `media/transcode.ts`：再加一道 `WRITING`（outPath → 完成信号）闸门，同一份产物只许一个
   ffmpeg 写；中间文件从 `<episodeId>.enc.mp4` 改成 `<产物名>.enc.mp4`，避免同一集不同档位互删。
   转码完成后校验 mp4 结构（`mp4IsSane`：遍历顶层 box，要求 moov 正好一个、mdat 存在、边界不越界），
   不合法直接丢弃重转。
3. `existingMedia` / `existingMediaAny` 复用前的校验从"大小 > 1KB"换成 `usableMedia`
   （大小 + `mp4IsSane`），坏文件自动删除、下次重转 —— 用户机器上已有的坏缓存会自愈。

## 2026-11-17 · 下拉菜单被卡片遮住（设置页全部中招）

- 菜单宽度按内容撑开（`width: max-content`），长选项不再被挤成两行；

   - 上游起不来（限流等）或转码失败：自动退官网 360p 直连（它支持 Range，进度条仍然完整），
     不会卡在"准备失败"；
   - 已缓存低档时仍然先播低档文件 + 后台升档（本来就是可拖的本地文件，没必要等）。
   - 推荐页（滑动场景）仍走"360p 先播、高清后台换源"，不受影响。
2. **预加载：等当前集 ready 之后再排**（否则当前集的转码和预加载抢 CPU，"第一集"等更久）。
3. **修掉预加载的死锁**（老代码的坑）：
   `schedulePreload` 里"已在跑就直接 return"，而收尾的
   `finally { if (gen === generation) running = false }` 在计划被新计划取代时**不会执行**，
   `running` 永远卡在 `true` → 之后这一进程内**再也不会预加载**。
   现在改成：新计划只覆盖 `latest`，常驻循环每轮读最新计划；收尾时若发现期间又排了新计划就补起一轮。
4. **转码闸门（前台优先、后台排队）**：`jobs.ts` 里加了 `acquireTranscode(foreground)`。
   原因：开「画质增强=strong」时一集 1080p 要 ~80s，而实际情况是
   「当前集转码 + 预加载转码 + 播到 25s 时的下一集预热」三路 ffmpeg 一起跑，
   CPU 被抢死，"等准备好"从 80s 变成 3 分钟以上（实测同一时刻出现 3 个 0 字节 `.part.mp4`）。
   现在：前台任务（`wait=1` 来的）永远立刻开；后台任务必须等**没有别的转码**在跑，且一次只放一个。

### 实测（dev 5881 + headless Edge 9338）

| 场景 | 结果 |
|---|---|
| 未缓存第 6 集（画质增强=关） | 等待层正常显示「取流中…」→「转码中 45%」；**8.8s** 后播 `/api/media/...-1080p.mp4`，duration=62 |
| 起播后拖到 60s | 落到 61.8s，正常 |
| 起播后预加载 | 2 分钟内转好 6 集（下一集优先）；跳到第 12 集后新计划继续跑（日志 `预加载完成（世代 7…）`），不再死锁 |
| 已在缓存的集（增强版） | **1.0s** 起播本地文件，duration=133.9，拖到 60s 落到 61.7s |
| 转码闸门：后台预加载在转时跳到另一集 | 前台等待层 1.5s 出现、14.4s 起播；**ffmpeg 并发峰值 = 2**（修复前是 3 路一起跑） |
| 连测自动下一集 3 轮（14→15→16→17） | 3/3，且全部命中预加载缓存，切换即播 |
| 画质增强=**strong** 时一集的 1080p 转码 | **约 80s**（x264 + hqdn3d/unsharp；开了增强就不会走 HEVC 直接搬运） |

> 说明：`画质增强=strong` 时单集转码 ~80s，"等准备好再播"意味着**新剧第一集要等 1 分多钟**，
> 预加载也基本只是"刚好跟上看剧速度"。想快就把画质增强关掉（实测 ~7~20s/集，或 HEVC 直接搬运 ~2s）。
>
> 另一个坑：**缓存文件名带增强后缀**（`<id>-1080p-strong.mp4` vs `<id>-1080p.mp4`），
> 复用只看同后缀的文件 —— 切换「画质增强」后，之前转好的那批会**全部不再命中**、得重转。
> 测试时为了跑得快把增强临时关掉，转出来的 27 个普通版缓存（730MB）在 strong 下不会被复用，已删除；
> 现在的缓存是 5 个 `-strong` 文件。验证完 `enhanceVideo` 已还原成 `strong`。

1. **官方链接参数含义和最初假设相反**（踩坑）：

   —— `video_id` 是**剧**（book），`vid`/`share_toast_vid` 才是**分集**。
   实测 `video_id=7687938296130833470` 调 `/api/series/` 是 469 集的《作死系统，非要让我去闯祸第二季》，
   `vid=7687958768876784665` 是第 3 集。原实现把 `video_id` 当分集、且拿不到 `book_id` 就放弃 → 认不出。

   只有剧 id（整部剧分享，挑"上次看到的那一集"，没有就第一集）；只有集 id 时明确报错。
